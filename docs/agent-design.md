# 에이전트 LLM 구성과 프롬프트 설계

마지막 갱신: 2026-11-02. 처음 만든 코드(1단계)와 앞으로 만들 에이전트(2~5단계)를 함께 정리한다.

## 1. 지금까지 만든 것 (1단계)

### LLM 호출 구조 — `core/llm.py`

| 항목 | 현재 값 | 이유 |
|---|---|---|
| 역할 | `writer`(작성), `judge`(평가) 두 가지 | 같은 모델이 자기 글을 채점하면 점수가 후해지는 편향을 줄이려고 |
| 기본 모델 | writer = Gemini `gemini-2.5-flash`, judge = OpenAI `gpt-4o-mini` | 블로그 자동화 앱에서 쓰던 Gemini 재사용 + 평가는 다른 회사 모델. 설정 화면에서 바꿀 수 있음 |
| 응답 형식 | 항상 JSON (Gemini `response_mime_type`, OpenAI `json_object`) | 화면에 점수·목록으로 나눠 보여주려고 |
| 온도 | 기본 writer 0.6, judge 0.2, 호출마다 바꿀 수 있음 | 작성은 표현이 다양하게, 채점은 매번 비슷하게 |
| 잘림 처리 | Gemini가 출력 길이 제한에 걸리면 바로 에러 | 블로그 앱에서 겪은 "JSON 반쯤 잘림" 문제 재발 방지 |
| JSON 파싱 | 코드펜스·앞뒤 잡문 제거, 실패 시 완화 모드 재시도 | 블로그 앱 `_extract_json` 그대로 |
| API 키 | `data/config.json` → 없으면 환경변수 | 공개 저장소라 키는 깃 밖에 둠 |

### 프롬프트 — 지금 실제로 동작하는 것은 1개

**경험 카드 추출** (`core/extract.py`, writer, 온도 0.2)

- 시스템: "문서에 실제로 적힌 사실만 옮긴다. 없는 수치·기간·성과는 만들지 말고 빈칸으로 둔다. JSON으로만 답한다."
- 사용자: 문서 전문(최대 6만 자) + 카드 필드 목록(STAR+V/L, 기술, 증빙) + 종류 목록
- 출력: `cards[]`와 `missing_questions[]`
  - `missing_questions`는 카드를 더 좋게 만들려면 사용자에게 물어야 할 것들이다. 블로그 앱의 성찰 질문과 같은 역할.
- 아직 실제 API로 돌려보지 않았다. API 키를 넣고 시험해야 한다.

## 2. 앞으로 만들 에이전트 구성

| 에이전트 | 모델 | 온도 | 입력 | 출력(JSON) | 넣는 작성 원칙 |
|---|---|---|---|---|---|
| 회사 리서처 | writer + 웹 검색 | 0.2 | 회사명, 공고 | 사업·이슈·인재상 + **출처 URL** + 직무 과제 | `analyze` |
| 공고 분석기 | writer | 0.2 | 공고 텍스트 | 필수/우대 요건, 키워드, 문항·의도·글자 수 | `analyze` |
| 매처 | writer | 0.3 | 경험 카드, 공고 분석 | 문항별 주 경험 카드 id, 배치 이유, 부족 정보 질문 | `match` |
| 작성기 | writer | 0.6 | 카드, 분석, 배치표 | 문항별 답변, **문장별 근거 카드 id** | `write` 또는 `resume` |
| 1차 사실성 검증 | judge | 0.2 | 답변, 카드 | 위반 문장·규칙 id·수정안 | `fact` |
| 2차 문항·구조 검증 | judge | 0.2 | 답변, 문항 의도 | 〃 | `write` |
| 3차 직무·회사 적합 검증 | judge | 0.2 | 답변, 공고 분석, 리서치 | 필수요건 커버리지 %, 회사명 바꾸기 테스트 결과 | `company_fit` |
| 4차 문장 품질 검증 | judge | 0.2 | 답변, 글자 수 제한 | 상투어·맞춤법·글자 수 | `write`(WR-3) |
| 5차 일관성 검증 | judge | 0.2 | 이력서·자소서·포트폴리오 | 문서 간 불일치 목록, 제출 체크리스트 | `final_check` |
| 수정기 | writer | 0.4 | 답변 + 검증 결과 | 고친 답변, 변경 이유 | 해당 회차 규칙 |
| 인사담당자 | judge | 0.3 | 최종안, 공고 | 항목별 점수, 판정, 이유, 면접 예상 질문 | 전체 요약 |

**회차 진행 방식**: 검증기(judge)는 문제를 찾기만 하고 직접 고치지 않는다 → 수정기(writer)가 고친다 → 다음 회차로 넘어간다.
검증과 수정을 분리해야 "고치면서 채점하는" 자기 합리화가 생기지 않는다.

## 3. 프롬프트 공통 틀

모든 에이전트 프롬프트는 같은 순서로 만든다.

```
[시스템]
1. 역할 한 줄 (예: "너는 10년 차 채용 담당자다")
2. 금지 규칙: 경험 카드에 없는 사실 금지, 남의 예시 문장 금지, JSON만 출력
3. 이 단계의 작성 원칙표 ← core.knowledge.principles("<단계>")

[사용자]
4. 입력 자료 (카드는 [id]가 붙은 cards_as_context 형식)
5. 할 일과 판단 기준
6. 출력 JSON 형식 (위반 사항은 반드시 규칙 id와 함께)
```

검증기의 출력은 `{"score": 0~100, "violations": [{"rule": "CF-1", "sentence": "...", "why": "...", "fix_hint": "..."}]}` 형태로 통일한다.
규칙 id가 있으니 화면에서 "회사명 바꾸기 테스트에 걸린 문장 2개"처럼 사람이 읽기 쉬운 형태로 보여줄 수 있다.

## 4. 유튜브 조사 보고서를 어떻게 썼나

[조사 보고서](research/2026-11-02-youtube-resume-cover-letter.md)(자소서 24편 + 이력서 24편)의 적용 포인트를
[작성 원칙](../knowledge/writing_principles.md) **36개 규칙**으로 바꾸고, 단계 7개(`analyze`, `match`, `write`, `resume`, `fact`, `company_fit`, `final_check`)로 나눴다.

- 규칙마다 **검사 방법**을 붙였다. 그래서 검증기가 "좋은 글인가?"처럼 막연하게 묻지 않고 구체적인 항목을 확인한다.
- 규칙마다 근거 영상 번호를 달아서 나중에 출처를 추적할 수 있다.
- 바로 쓸 수 있어서 특히 유용한 규칙:
  - **CF-1 회사명 바꾸기 테스트** (자12): 지원동기가 다른 회사에도 그대로 통하면 근거가 약하다는 신호
  - **WR-5 지원동기 둘로 나누기** (자20): 회사를 고른 이유와 직무를 하려는 이유
  - **MA-1 문항 간 경험 중복 금지** (자3)
  - **RS-2 수치에는 기준과 기간** (이5)
  - **FC-2 문서 간 날짜·기간 일치** (이23)
- 보고서의 한계도 그대로 따른다. 영상 조언은 절대 규칙이 아니고 최신 공고가 우선이며, 제목에 나온 합격률 수치는 쓰지 않는다.
- 보고서는 각 50편 목표 중 24편씩만 채운 상태다. 영상을 더 조사하면 규칙표만 고치면 되고, 코드는 바꿀 필요가 없다.

## 5. 직무군 프롬프트 (2026-11-02 추가)

직무군 6개 서류 평가 기준 조사 보고서(채용공고·현직자 글·NCS 등 출처 링크 포함, 지원자 경력이 들어 있어 비공개 `data/research/`에 보관)를 바탕으로 직무군 6개 × 세부 직무 19개 기준을 [knowledge/groups/](../knowledge/groups/README.md)에 만들었다.

- 직무군 파일마다 `overview / hard_filters / matcher / writer / resume / judge` 6부분이 있다.
- `core/prompts.py`의 `build_system_prompt(agent, subrole)`가 **역할 → 규칙 → 공통 원칙 → 직무군 기준 → 내 이야기 각도 → 출력 형식**으로 조립한다. 에이전트 4종(matcher·writer·resume·judge) × 세부 직무 19개 = 76개 조합이 모두 조립되는 것을 확인했다.
- 개인 경력에 맞춘 각도는 비공개 `data/angles.md`에 두고, 작성 단계(매처·작성기·이력서)에만 넣는다. 인사담당자에게는 넣지 않는다. 지원자의 의도를 모르는 상태에서 채점해야 하기 때문이다.
- 직무군마다 AI 경험의 무게가 반대다. 전기 시공·현장 설비에서는 줄이고, AI 컨설팅·스타트업 개발에서는 판단·검증 구조로 앞에 둔다.

## 6. 남은 과제

- [ ] 경험 카드 추출을 실제 API로 시험하기 (키 필요)
- [ ] 직무군 프롬프트를 실제 공고 1~2개로 시험해 채점이 직무군답게 나오는지 확인
- [ ] 평가 모델이 작성 모델보다 약하면 검증 의미가 줄어든다 → 평가 모델 선택 기준을 정해 기본값 다시 보기
- [ ] 문서가 6만 자를 넘으면 지금은 잘라서 보낸다 → 문서별로 나눠 추출 후 합치기
- [ ] 프롬프트·응답 기록(`data/runs/`)을 남겨서 회차별로 무엇이 바뀌었는지 추적하기
- [ ] 같은 입력으로 여러 번 돌렸을 때 채점이 흔들리는지 확인하기 (평가 일관성)
