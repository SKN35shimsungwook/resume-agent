## 직무군 개요: 스타트업 개발

- **하는 일**: AI 기반 서비스 개발 + 프론트/백엔드 + 배포·운영 + 타 부서 협업을 한 사람이 맡는다. AI 애플리케이션 쪽은 LangChain·LangGraph 에이전트, LLM API 연동, RAG·벡터 DB, 정부과제 참여까지. 대기업보다 역할 경계가 흐리고 교육 체계가 약하다.
- **핵심 증거 문법**: 문제 → AI 활용 방식 → 검증 → 수치, 그리고 배포 URL.
- **AI 경험의 무게**: 기본값. 질문이 "AI 쓸 줄 아세요?"에서 **"AI로 뭘 바꿔봤어요?"**로 바뀌었다. AI 도구 사용은 감점이 아니고, **AI가 만든 결과를 설명·검증하지 못하는 것**이 감점이다.
- **당락 요인**: 본인 경험에서 찾은 문제를 해결한 프로젝트, 기술 선택 이유, 검증 방법, 지표, 배포·운영 흔적. 비슷비슷한 교육 과정 클론 프로젝트와 스택 나열은 탈락 패턴.
- **서류 형식**: 확인한 공고는 자소서가 자유 양식 1개이거나 없었고, 포트폴리오·경력기술서 PDF가 필수였다.

## 확인 항목: 스타트업 개발

공고가 요구하는 기본 요건이다. 못 채워도 지원은 한다. 매처는 충족 여부만 표시하고, 작성기는 부족한 요건을 먼저 꺼내지 않는다.

- 경력 요건: 대부분 1~3년. "이에 준하는 AI 서비스 개발 경험"을 인정하는 공고가 있다 → 그 문구가 있는지 확인
- 포트폴리오·경력기술서 PDF 필수 여부
- 배포 링크가 살아 있는지

## 작성 지침: 스타트업 개발

**반드시**
- 대표작을 **문제 → 접근 → 내 역할 → 검증 → 결과 수치 → 회고**로 깊게 쓰고, 나머지는 "기타 N개" 한 줄로 묶는다.
- AI 협업 방식을 숨기지 않는다. 무엇을 AI에 맡기고 무엇을 직접 판단했는지(프롬프트·리뷰·평가셋·실패 사례) 쓴다.
- 기술 선택 이유와 트레이드오프(비용·지연·품질)를 쓴다.
- 실제로 해 본 것만 스택에 쓰고, 없는 경험(FastAPI·DB·Docker·사용자 피드백 등)은 갭으로 두거나 학습 계획으로 쓴다.
- 기획·고객 접점까지 하는 개발자로 포지셔닝한다.

**금지**
- 레포 개수·커밋 수를 헤드라인에 두기(한 줄 지표로만)
- 튜토리얼 클론을 대표작으로 두기
- "AI로 구현"만 있고 본인 역할이 빈 서술
- 모든 프로젝트를 같은 무게로 나열
- 죽은 배포 링크, 실행법·문제·결과 없는 README 링크
